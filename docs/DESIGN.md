# Почему перевод атомарен

`Ledger::transfer` открывает отдельное libpq-соединение. RAII-объекты владеют `PGconn` и `PGresult`; `Transaction` вызывает ROLLBACK при исключении. Успешный COMMIT — последняя операция перед ответом.

1. INSERT резервирует уникальный ключ перевода внутри транзакции. Конкурентный запрос с тем же ключом ждёт завершения первой транзакции. Если первая откатится, второй сможет выполнить INSERT.
2. При конфликте SELECT в отдельной команде READ COMMITTED видит зафиксированную строку. Сравнивается весь значимый payload: оба счёта и сумма. Повтор не вычисляет ответ из текущего баланса.
3. Оба счёта читаются `ORDER BY id FOR NO KEY UPDATE`. Один порядок предотвращает цикл блокировок при встречных переводах. `NO KEY UPDATE` совместим с KEY SHARE, который берут FK-проверки при INSERT перевода; обычный FOR UPDATE здесь мог бы создать взаимную блокировку при повышении уровня.
4. Проверяются средства и верхний предел. Два UPDATE и две проводки входят в ту же транзакцию.
5. Ошибка любого SQL откатывает весь перевод. Тест добавляет ограничение на счёт-получатель: второе UPDATE падает после первого, после чего проверяются оба баланса и отсутствие строк перевода/проводок.

## Что гарантирует БД, а что приложение

PK защищает уникальность ключа. FK защищают ссылки. CHECK запрещает отрицательный/чрезмерный баланс, неположительную сумму и перевод себе. Соответствие суммы проводок нулю обеспечивает код одной транзакции, отдельного deferred trigger в этой версии нет. Внешний прямой SQL может нарушить соответствие `balance` и проводок; прикладной API не предоставляет редактирование истории.

## Ошибки и нагрузка

Восемь HTTP-потоков, очередь 32 соединения, лимит тела 4 KiB, read/write timeout 2 секунды. PostgreSQL statement_timeout 3 секунды, lock_timeout 2 секунды. DSN должен задавать connect_timeout; Compose и CI задают 3 секунды. Один запрос может выполнить несколько SQL-команд, поэтому это не общий дедлайн запроса. При перегрузке библиотека может закрыть соединение: гарантированный JSON 503 для каждого переполнения не обещается.

После потери соединения на COMMIT клиент не знает, была ли фиксация. Сервер не выдумывает ответ об откате: клиент повторяет прежний ключ, БД возвращает сохранённую операцию или выполняет её впервые. Начальные балансы — явно учебная модель, не эмиссия реальных средств.

## Следующие измеримые улучшения

Пул соединений с ограниченным ожиданием, общий дедлайн, постраничная история, измерения p50/p95/p99 и запросов/с с указанием оборудования. Они пока не реализованы и не заявляются в резюме.
