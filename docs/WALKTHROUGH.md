# Маршрут по коду

1. `sql/001_schema.sql`: какие нарушения запрещает схема? Какие остаются ответственностью сервиса?
2. `include/ledger/ledger.hpp`: публичные структуры, пределы чисел и доменные ошибки.
3. `src/ledger.cpp`: владение libpq-ресурсами, параметры SQL, границы транзакции, блокировки и повтор по ключу.
4. `src/main.cpp`: HTTP-контракт, строгие JSON-типы, сервисный токен, ограничения сервера и завершение по сигналу.
5. `tests/integration.py`: сценарий после первого UPDATE, конкурентные списания и встречные переводы.

Практика: запустить тесты; временно убрать проверку payload при повторе и убедиться, что тест падает; вернуть код. Затем убрать блокировку счетов и сравнить результаты конкурентных тестов. Не публикуйте сломанную версию в main.

Вопросы для обсуждения: почему нельзя хранить сумму в double? Что происходит после неизвестного результата COMMIT? Почему порядок блокировок важен? Почему для FK здесь выбран NO KEY UPDATE? Чем атомарность отличается от идемпотентности? Как не допустить бесконечного роста истории?
